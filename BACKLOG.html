3. The next three, with pass criteria

Not the best three. The three that are worth doing before anything else, in order, each with the number that decides whether it worked.

Q1 and Q2 together — one app-proxy build, one deploy, one revert. They live in the same file tree and they finish wave three's §3.6, the section that started all of this. Pass: deploy twice; the first tab shows the notice without being forced; one reload lands the second build id; with the network cut, the page still says something ours and a typed message survives the reload. Fails if: the notice appears while someone is typing, or an offline draft is shown as sent.

Q3 — the index tells the truth. Pass: search a cold channel and watch it fill with a count; then confirm the next message indexes without a search. Fails if: an empty result and an empty index look the same on screen.

Q4 — the first hour. Pass: a fresh test account receives exactly one message, on one line, with no exclamation marks, and finds three pinned items in one channel. Fails if: it arrives twice, or a second join sends a second welcome.

After those three, Q5 costs nothing and can run in parallel with anything: it is three uploads and a drawing of the mascot twelve times.

6. When to write another document

One condition, and it is not "the owner asked". Write another plan only when a measurement contradicts this queue — a row that turns out to be already built, a defect that is worse than described, or a new number that changes the order of §3.

What does not justify another document: a new idea, because new ideas go in the rejected table with a reason; a re-reading of an old wave, because the retirement table already says what each is for; or the fact that planning is easier than building.

The queue is nineteen items deep and six have been built. Nineteen is not a backlog problem, it is a Tuesday. The next action is Q1 and Q2, and it is code.
